# Agent Knowledge Base

> Read this file in full before starting any task. It is the authoritative reference for all project conventions, patterns, and gotchas. Update it whenever you discover new knowledge during development. **Keep this file in context for the entire duration of every task** — do not let it scroll out of context mid-task. If context pressure forces a choice, preserve this file over other read content.

**Maintenance rules:**

- Reduce duplication: cross-reference sections instead of repeating information.
- Point to actual project files rather than duplicating their content here.
- When updating, consolidate similar information; do not add standalone "new discovery" sections.
- Knowledge that only matters for one kind of task (writing tests, images, blog MDX, etc.) belongs in a project skill at `.agents/skills/<name>/SKILL.md` (`.claude/skills` is a symlink to it, for Claude Code), not here — this file is loaded in every session. When recording a non-obvious learning: update the existing skill covering that task type; if it is specialised and no skill fits, create one (a `description` that states the trigger first, and narrow `paths:` globs only when a tight file set exists); if it applies across the board, add it here. Do not list skills in this file.

## Claude Code marketplace (plugins)

- This repo is a Claude Code marketplace holding several mods under `plugins/<name>/`, listed in `.claude-plugin/marketplace.json`. The tooling (package.json, ESLint, Prettier, husky) is shared at the root; the scripts loop over `plugins/*`, so a new plugin needs no script or CI change. See the README's Layout.
- A plugin's hooks import types from `'claude-code'`, which only exist after the engine lays them into `plugins/<name>/.claude-plugin/types/` (gitignored, generated by `pnpm types:gen`).
- Setup, running, scripts and prerequisites are in `README.md`; the generation script is in `package.json`.
- CI (`.github/workflows/check.yml`) runs `types`, `lint`, `format`, `validate` and `test` as separate jobs, each using the `.github/actions/setup` composite action. CI generates the types with a placeholder API key, because the engine writes them before the model call fails; see the comment in that action.
- A function that receives `$` and lives in another file must be a `function` declaration, not a `const` arrow, or `claude plugin validate` rejects it.
- The CLI version CI installs is pinned in `.github/actions/setup/action.yml` and bumped by Renovate through its `# renovate:` comment (the shared preset's `customManagers:githubActionsVersions`). `validate` and `test` need neither a login nor the generated types.
- Type-aware ESLint (`projectService`/`project`) was tried and abandoned: a single typed rule ran for over 3 minutes without finishing on this tiny repo, while `tsc` takes under a second.
